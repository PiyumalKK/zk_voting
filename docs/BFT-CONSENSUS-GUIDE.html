How this election reaches agreement

The chain used to have one writer. It now has four validators who vote, and a block counts only when three of them sign it. This is what changed, why it had to, and how to prove it works.

Before · single sequencer
One machine decides, and one machine can stop it.
Replicas could detect a bad block. They could not produce a good one.
Now · 2/3 BFT consensus
Three of four parties must agree before a vote is final.
Survives losing any one validator. Halts rather than weaken if it loses two.
01

The old model, and the two things wrong with it

It is worth being precise about the weakness, because the fix is shaped exactly around it.

Until now the chain had one writer. A single machine — node1, the primary or sequencer — received every transaction, executed it, and sealed it into a block. The other three were replicas: they received each finished block, re-executed it to check it was honest, and stored it.

That design has real virtues. There are no forks, because only one machine ever writes. And the replicas are not gullible — they re-execute everything, so a primary that lied about a state root would be caught immediately.

Weakness 1 — availability

If node1 dies, the election stops. Not degrades — stops. The three healthy replicas can copy blocks but have no mechanism to propose one. Nobody can vote until it comes back. For a system whose whole job is accepting votes inside a fixed window, "one server reboot ends the election" is not survivable.

Weakness 2 — trust

Detection is not prevention. A replica can prove a state root is wrong, but it cannot stop node1 from omitting a valid vote, reordering transactions, or otherwise deciding what the chain contains. Whoever runs node1 decides the election's contents — and in a real vote that party is the electoral authority.

What we want instead

No single party can stop the election. No single party can decide its contents. Everything below is the machinery for those two sentences.

02

The new model: four validators, three signatures

The same four machines. What changed is that all four may now write, and none of them may write alone.

Instead of one machine that writes and three that watch, there are four machines that vote. They take turns proposing blocks, and a block becomes real only when a quorum agrees. The four are the parties with a stake in the outcome:

The political point, not just the technical one

Names are cosmetic to the protocol — the code only ever deals in addresses. But the arrangement is deliberate: the parties who would otherwise have to trust the authority are inside the machine that decides.

03

Why four validators, and why three signatures

These numbers are not a preference. They fall out of two requirements that pull in opposite directions.

Let N be the number of validators, Q the signatures a block needs to be final, and f the number that may be faulty — crashed, unreachable, or actively lying.

Requirement A — liveness

The election must continue when f validators are down. The survivors must still be able to reach Q: 

Q ≤ N − f

Requirement B — safety

Two different blocks must never both be finalized at one height. Any two groups of Q drawn from N overlap in at least 2Q − N members, and at least one of those must be honest: 

2Q − N > f

Substituting A into B gives the whole answer:

2(N − f) − N > f    →    N − 2f > f    →    N > 3f

You need more than three times as many validators as faults you want to survive. To survive one: N > 3, so N = 4 is the minimum. The smallest Q satisfying both is Q = ⌈2N∕3⌉ = 3.

04

What the validator keys are

Four keys were generated before anything was deployed. They are not accounts, and it is worth being exact about what they do.

Each validator holds a secp256k1 private key — the same cryptography as an Ethereum account key. But it is not an account: it holds no funds, sends no transactions, and never appears on-chain. Its only job is to sign that validator's votes.

Every node needs the addresses of all four in order to check signatures. That list is VALIDATOR_SET, identical on all four machines — which is why four keys produce four addresses, and why the addresses are published while the keys are not.

Private key — secret

One per machine. Held in a GitHub Actions secret, written to data_3001/keys/validator.key at mode 0600. Never in git, never in an Environment= line — so it appears in neither ps -e nor systemctl show.

Address — public

Derived from the key by a one-way function. Published in gen_inventory.py and held by every node. Publishing it lets everyone verify signatures; it does not let anyone produce them.

Order is protocol-significant

VALIDATOR_SET is an ordered list, because whose turn it is to propose is computed as validators[(height + round) % 4]. Two nodes given the same members in a different order would disagree about whose turn it is at every height, and the chain would never move. A node also refuses to boot if its key does not derive to the address listed for its own ID — a validator signing with an unlisted identity is otherwise invisible.

The instructive pair

mTLS decides who may speak. The consensus key decides whose word counts toward a quorum. Someone holding a stolen certificate can connect and be completely ignored.

05

What happens when someone votes

The full journey for one ballot, from tap to final. Four phases, and a fifth that only runs when something goes wrong.

The part that matters most

A PREPARE does not mean "the proposer says this is fine". It means "I executed this block myself and reproduced every value its header commits to" — using the same code the offline auditor runs. A validator never takes a peer's word for anything, including while catching up after a restart.

The lock — why a traitor cannot fork the chain

The instant a validator broadcasts a COMMIT it locks onto that block for that height, and will never vote for a different one there in any later round. Since any two groups of three share at least one honest member, two different blocks would need that honest node to have committed to both. It cannot.

06

What happens as validators fail

The threshold is the whole design. Below it, the correct behaviour is to stop.

And if keys are compromised rather than machines lost

Keys stolenWhat the attacker can doOutcome
1 Nothing. This is exactly the fault the system is built to absorb. absorbed
2 Cannot finalize anything (2 < 3). Can halt the election by refusing to vote. denial of service
3 Controls ordering; can censor. Still cannot finalize an invalid state root — honest validators re-execute before voting. control
The security claim, stated plainly

Three of the four parties must collude. Compare that with the previous design, where compromising one machine was enough. Note also what even three cannot do: forge a vote count. The attack surface is ordering and censorship, not arithmetic.

07

The commit certificate

The three signatures are stored with the block. This is what makes the whole design auditable from outside.

Ask any node for any block's certificate and you get the signatures, the addresses they recover to, and how many were required. The addresses are recovered from the signatures by the server, not read from a configuration file — so a scrutineer can check the arithmetic without trusting the node that served it.

Request
curl -s http://<node>:3001 \
  -H 'content-type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,
       "method":"zk_getCommitSeals",
       "params":["latest"]}'
Response
{
  "number": "0x2a",
  "blockHash": "0x9f3c…",
  "quorum": "0x3",
  "validatorSetSize": "0x4",
  "seals": [
    { "validator": "authority", "address": "0x5417…" },
    { "validator": "jvp",       "address": "0xC6E4…" },
    { "validator": "unp",       "address": "0x4Cb1…" }
  ]
}
Why the signatures sit beside the block, not inside it

Most IBFT chains pack seals into the block header. This one cannot: the block hash and state root are what the auditor, the replicas and the replay engine all verify against, so putting signatures into the hashed header would change every block hash — the same votes would produce a different chain, and every piece of existing verification code would need a second path. The certificate is therefore a sidecar, keyed by block height and hash.

The honest cost of that choice

A block's validity does not depend on its seals. Re-executing the chain proves the state is right; the seals prove who agreed to it. Losing a seal record loses audit trail, not the block — which is why a missing certificate returns null rather than an error.

Why the network needed no change

The security group already carried from_port 4001, self = true. That rule is membership-based rather than pair-based, so the full mesh already existed — the single-sequencer design simply never used it in both directions.

There is no replica in a BFT cluster

A replica cannot propose, so a validator configured as one would hold a key, be counted in the quorum, and never take its turn — leaving the cluster permanently one vote short. The node refuses to boot in that configuration.

Ansible generates the inventory from Terraform's output. Under BFT, every host gets its own peer list — previously only node1 got one:

09

Demonstrating it

The whole value is that these are observable on real machines. Rehearse them; do not run them for the first time on the day.

  1. Baseline. /health shows "role":"validator" on all four — not "primary". Cast a vote; its certificate shows three distinct addresses. Say: "three of the four parties independently re-executed this block and signed it."
  2. Kill the authority. sudo systemctl stop zk-node on node1. Cast a vote — it lands. zk_consensusStatus shows the proposer has rotated away, and the new block's seals do not include the authority's. Say: "the electoral authority's server is off and voting continues. Under the old design this stopped the election entirely."
  3. Kill a second. Cast a vote — it fails after roughly 24 seconds with consensus did not reach quorum… it was not mined. Heights on the survivors are frozen; every block still shows three seals. Say: "it stops rather than letting two parties agree a result between themselves."
  4. Restore one. It re-executes every block it missed, verifying each itself, then rejoins voting. Resubmit; it lands.
  5. Run the audit. go run ./cmd/audit -data-dir ./data_3001 — every block re-executes to the state root it always did. Say: "consensus changed who decides the order. It did not touch execution."
The demo that matters most is number 3

Anyone can build something that keeps going. Stopping for the right reason is the engineering. Two of four gone means the remaining two must not be able to decide an election between themselves — and the system enforces that rather than degrading.

10

Honest limitations

Every one of these is a deliberate trade rather than an oversight. Being able to name them is part of the work.

The validator set is fixed at configuration
There is no on-chain membership management. Changing the set means deciding at which block it changes, which affects the certificates of blocks either side — so it is a coordinated restart of all four.
Two validators down halts the election
Correct by design: two of four must not be able to decide anything. It is a liveness cost accepted in exchange for the safety guarantee.
The proposer executes each transaction twice
Once building the candidate, once committing it through the same path a follower uses. Bought deliberately: it leaves exactly one durable write path, so a block this node proposed and a block it received are indistinguishable on disk.
The audit does not verify seals
It re-executes the chain, which is the stronger check. Cross-checking every historical certificate is possible future work.
One operator generated all four keys
A convenience of this deployment. In a real election each party generates its own key on its own hardware and publishes only the address — the protocol does not assume otherwise. This is a property of the deployment, not a flaw in the design.
11

In one paragraph

The chain previously had a single writer, which meant one machine could stop the election and one party decided its contents. It now runs QBFT-style Byzantine fault tolerant consensus across four validators — the electoral authority and three political parties — each holding a cryptographic signing key. Validators take turns proposing blocks by a formula every node computes independently; each validator re-executes a proposed block itself before voting; and a block becomes final only when three of the four have signed a commit for it, with those three signatures stored alongside it as a verifiable certificate. With four validators and a threshold of three, the system survives any one validator failing — the election continues even with the authority's server switched off — and halts rather than weakening if two fail, because allowing two parties to agree a result would defeat the point. Forking is impossible even against an actively malicious validator, because any two groups of three share at least one honest member, and an honest validator never commits to two blocks at the same height.
