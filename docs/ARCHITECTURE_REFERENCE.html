01  System

System overview & actors

The system lets a citizen prove they are an eligible, registered voter and cast exactly one vote — without revealing who they are. Officials run a web app; voters use a phone.

The four actors

ActorClientDoesKey code
Admin (Election Commission)WebCreates a Voting contract per polling division, sets question/candidates, drives phase transitions, assigns GN officers.nextjs/app/voting/admin/page.tsx
GN Officer (Grama Niladhari)WebEnrolls voters for their own division only (allowlist + NIC dedup). Cannot change the election.nextjs/app/gn/register/page.tsx
VoterMobileGenerates a hardware key, registers a ZK commitment, then casts one anonymous vote.mobile/app/*.tsx
Observer / publicWebReads live results, national aggregate, and audits any nullifier without de-anonymising it.nextjs/app/results, app/audit
Key idea — separation of duties No single role can both enroll a voter and be that voter. The Admin owns the election, the GN owns enrollment, and the voter owns their secret. Anonymity does not depend on trusting any of them — it is enforced by the ZK proof.

03  Mechanism

The exact voting mechanism

This is the behind-the-scenes walkthrough of how the current implementation actually works — verified against the code. It rests on three primitives (a Poseidon commitment, a nullifier, a Merkle inclusion proof) wired across five stages: Setup → Enroll → Register → Vote → Verify.

The two secrets and what's derived from them

packages/mobile/src/services/crypto.tslines 33–43
/** Generate a fresh voter commitment (called once, during registration). */
export function generateCommitment(): VoterCommitment {
  const nullifier = randomFieldElement();
  const secret = randomFieldElement();
  const commitment = poseidon2([nullifier, secret]);   // tree leaf
  const nullifierHash = poseidon1([nullifier]);       // double-vote guard
  return { nullifier, secret, commitment, nullifierHash };
}

What the circuit actually proves

The Noir circuit takes the two secrets as private inputs and the nullifierHash, root, vote and depth as public inputs. It enforces four constraints:

packages/circuits/src/main.nrmain(...)
fn main(
  nullifier_hash: pub Field,        // public
  nullifier: Field, secret: Field,  // private — never leave the phone
  root: pub Field, vote: pub Field, depth: pub u32,
  index: Field, siblings: [Field; 16],  // private Merkle path (max 2^16 leaves)
) {
  // 1 · the revealed hash really comes from the hidden nullifier
  assert(hash_1([nullifier]) == nullifier_hash);
  // 2 · reconstruct this voter's leaf
  let commitment = hash_2([nullifier, secret]);
  // 3 · that leaf is in the tree with the given root
  let computed_root = binary_merkle_root(hash_2, commitment, siblings_num, index_bits, siblings);
  assert(computed_root == root);
  // 4 · bind the vote to the proof (anti front-running) + range-check 0..255
  let _vote_bits: [u1; 8] = vote.to_le_bits();
}
Key idea — the nullifier does double duty It is hidden inside the commitment (so the leaf can't be linked to a person) and its hash is revealed at vote time (so the same voter can't vote twice). The contract stores used nullifierHashes; a repeat reverts with Voting__NullifierHashAlreadyUsed.

Stage A · Setup — the admin builds the election (no genesis question)

The Election Commission deploys the shared libraries once (PoseidonT3, LeanIMT, HonkVerifier), then a NicRegistry and an ElectionRegistry. For each polling division it deploys a separate Voting contract — the question and candidate list are passed straight into the constructor.

Stage B · Enrollment — the GN officer allowlists a voter (before they register)

The voter first opens the mobile app, which mints a keypair inside the phone's secure hardware and shows the device address as a QR code. The GN officer scans it and enrolls that address — gated by a NIC uniqueness check that spans all divisions.

Stage C & D · Register and Vote — the two on-chain moments

Stage D in detail · who does what when a vote is cast

The vote is the subtle part. Three parties cooperate, but no secret ever leaves the phone: the server only ever touches public data, and the chain only ever sees a proof.

mobile/app/vote.tsxcastVote() — the real sequence
const { commitment } = deriveFromSecrets(secrets.nullifier, secrets.secret);
const path = await api.getMerklePath(division.votingContract, commitment); // server rebuilds tree
const callData = await generateVoteCallData({ nullifier, secret,       // on-device ZK proof
    circuitIndex: path.circuitIndex, siblings: path.siblings, root: path.root,
    candidateIndex: candidate, depth: path.depth });
const burner = newBurnerAccount();                // anonymous sender
await api.fundBurner(burner.address);
await submitVote(division.votingContract, callData, burner.privateKey);

Stage E · Verify & tally — anyone can audit, no one is de-anonymised

After voting, the app can prove your vote counted without revealing you: it derives your nullifierHash locally and asks GET /api/verify-vote, which checks isNullifierUsed() on-chain and scans VoteCast events. Because the nullifier hash is already public and unlinkable to identity, this leaks nothing. Live tallies come from each division's getVoteCounts(), and ElectionRegistry.getNationalResults() sums them across divisions.

Key idea — where each guarantee actually lives Eligibility = the GN's on-chain allowlist. One-person-one-registration = NicRegistry hashed-NIC. Anonymity = the ZK proof + burner sender. One-vote = the on-chain nullifier-hash set. No single component carries two of these, which is why compromising one doesn't collapse the others.
04  On-chain rules

Smart contracts

Four contracts. Voting.sol is one election; ElectionRegistry turns it into a national, division-per-contract system; NicRegistry stops the same citizen registering twice; Verifier checks the ZK proof.

hardhat/contracts/Voting.sol251–263
function register(uint256 _commitment)
    external inPhase(Phase.Registration) {
  if (!s_voters[id][msg.sender]
      || s_hasRegistered[id][msg.sender])
    revert Voting__NotAllowedToVote();
  s_commitments[id][_commitment] = true;
  s_hasRegistered[id][msg.sender] = true;
  s_trees[id].insert(_commitment);   // Poseidon
  emit NewLeaf(s_trees[id].size-1, _commitment);
}
hardhat/contracts/Voting.sol267–304 · vote()
function vote(bytes _proof, bytes32 _nullifierHash, bytes32 _root, bytes32 _vote, bytes32 _depth)
    external inPhase(Phase.Voting) {
  if (_root != bytes32(s_trees[id].root()))  revert Voting__InvalidRoot();      // proof must target the live tree
  uint256 candidateIdx = uint256(_vote);
  if (candidateIdx >= s_candidates.length)     revert Voting__InvalidCandidate(candidateIdx);
  bytes32[] publicInputs = [_nullifierHash, _root, _vote, _depth];
  if (!i_verifier.verify(_proof, publicInputs)) revert Voting__InvalidProof();        // ← HonkVerifier + BN254
  if (s_nullifierHashes[id][_nullifierHash])   revert Voting__NullifierHashAlreadyUsed(_nullifierHash);
  s_nullifierHashes[id][_nullifierHash] = true;   // double-vote guard
  ++s_voteCounts[id][candidateIdx];                // tally
}

Watch out — invariant A proof is generated against a specific Merkle root. If anyone registers after the proof is made, vote() reverts with Voting__InvalidRoot. In practice registration closes before voting opens, which is exactly why the phases are separate.

06  Custom chain

Custom Go blockchain

A single Go binary that embeds a real Geth EVM and runs the exact Hardhat bytecode — but with an authority model: no mining, no gas, no wallets. Writes arrive as REST calls; every write executes in the EVM before a block is committed.

Key idea — the hand-written bridge is the price of the design Unlike scaffold-eth (auto-generated bindings), the Go node exposes one typed method + one REST endpoint per contract function, written by hand. The payoff is decoded revert errors, pre-commit validation and caching. The cost: a contract change must be threaded through bridge.go → types.go → replay.go → server.go → API.md. That checklist lives in blockchain/CONTRACT_CHANGE_CHECKLIST.md.

Why a burner wallet?

Registration is signed by the voter's own hardware key (they're on the allowlist). Voting is sent from a fresh, throwaway key so the on-chain msg.sender can't be linked back. Anonymity comes from the proof, not the sender.

export function newBurnerAccount() {
  const pk = generatePrivateKey();
  return privateKeyToAccount(pk); // unlinkable
}
Gap — on-device prover & Hardhat coupling Two things to know before extending the app: (1) the native Barretenberg prover is wired but requires an expo prebuild step to leave Expo Go (see mobile/README.md); (2) config.ts defaults to chainId 31337 and a Hardhat RPC — the app currently assumes the EVM backend, not the Go node.

10  Extending

Gaps & where to extend

The architecture is sound; the main incompleteness is that the newest features live on the EVM/Hardhat side and haven't been threaded back into the custom Go chain or fully productionised.

#GapImpactWhere to start
1Custom chain is single-election only. No ElectionRegistry, NicRegistry, GN role or divisions in the Go node (its assets/ embeds only Voting.json).Custom backend can't run the division/GN/NIC flow; those features are Hardhat-only today.Follow CONTRACT_CHANGE_CHECKLIST.md: embed the two new artifacts, add bridge methods, TxTypes, replay cases, endpoints.
2Mobile app assumes Hardhat. config.ts hardcodes chainId 31337 + JSON-RPC; it signs EVM txs via viem.App won't work against the Go node's REST API without an adapter.Add a REST submit path mirroring nextjs/services/chain/restClient.ts.
3On-device prover not turned on by default. Witness building is done; native Barretenberg needs expo prebuild.Proof generation is stubbed/limited in Expo Go.mobile/src/services/nativeProver.ts + README checklist.
4Dev-only auth shortcuts. /api/faucet uses a well-known key; OTP uses a mock provider.Not production-safe as-is (by design, guarded to local chains).Swap in a paymaster/relayer and Twilio/Firebase; both are isolated behind their service modules.
5Frontend REST adapter lags the EVM adapter. restClient.ts covers only the original Voting surface.Division-aware pages only work on Hardhat.Extend the ChainAdapter and implement both branches (§5).
The one document to keep open while extending packages/blockchain/CONTRACT_CHANGE_CHECKLIST.md enumerates every file that must change when a contract changes: artifacts → bridge.go → core/types.go → replay.go → server.go → API.md → tests → frontend adapter. Treat any new contract function as a full pass down that list.

Suggested first milestone

Bring the custom Go chain to feature parity with the EVM path for a single division: it already runs Voting.sol end-to-end. The highest-leverage next step is deciding whether the Go node should (a) expose a thin JSON-RPC shim so the existing mobile app and division-aware routes work unchanged, or (b) gain REST endpoints for ElectionRegistry/NicRegistry and have the clients grow a REST branch. Option (a) minimises client churn; option (b) keeps the node's "typed REST" philosophy intact.
