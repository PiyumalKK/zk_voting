\chapter{Smart Contracts and Custom Blockchain}\label{ch:contracts}

This chapter presents the complete implementation of our smart contract layer and custom Go blockchain. We analyze each contract in detail---state variables, events, modifiers, and functions---then describe the custom blockchain architecture: a contract-agnostic node that embeds the go-ethereum EVM behind an Ethereum JSON-RPC interface, providing gasless execution, replicated persistence, independent auditability, and wallet-free administration.

\section{Voting.sol: Per-Division Election State Machine}

\texttt{Voting.sol} is the core contract implementing a complete election lifecycle for a single polling division. It moves through four phases---\texttt{Setup}, \texttt{Registration}, \texttt{Voting}, \texttt{Ended}---with admin-driven transitions and deadline-based auto-advancement.

\subsection{State Variables}

All per-election state is keyed by a monotonic \texttt{s\_electionId}, so \texttt{resetElection()} can start a fresh election by bumping the counter---cheaply ``clearing'' every mapping without iteration:

\begin{lstlisting}[language=Java, caption={Voting.sol state variable declarations.}]
uint256 public constant MAX_CANDIDATES = 100;
IVerifier public immutable i_verifier;

// GN officer address -- may call addVoters() for this division
address public s_gnOfficer;

// Monotonic election counter; keys all per-election state below
uint256 private s_electionId;

string private s_question;
string[] private s_candidates;
// electionId => candidateIndex => count
mapping(uint256 => mapping(uint256 => uint256)) private s_voteCounts;

Phase private s_phase;
uint256 private s_registrationEndTime;
uint256 private s_votingEndTime;

// electionId => voter => allowlisted / hasRegistered
mapping(uint256 => mapping(address => bool)) private s_voters;
mapping(uint256 => mapping(address => bool)) private s_hasRegistered;
// electionId => commitment => used
mapping(uint256 => mapping(uint256 => bool)) private s_commitments;
// electionId => nullifierHash => used
mapping(uint256 => mapping(bytes32 => bool)) private s_nullifierHashes;

// electionId => Merkle tree (LeanIMT)
mapping(uint256 => LeanIMTData) private s_trees;
\end{lstlisting}

\subsection{Modifiers}

\begin{lstlisting}[language=Java, caption={Phase enforcement and access control modifiers.}]
modifier inPhase(Phase expected) {
    _maybeAdvancePhase();  // Auto-advance if a deadline passed
    if (s_phase != expected) {
        revert Voting__WrongPhase(expected, s_phase);
    }
    _;
}

modifier onlyOwnerOrGN() {
    require(msg.sender == owner() || msg.sender == s_gnOfficer,
            "Not owner or GN");
    _;
}
\end{lstlisting}

The \texttt{\_maybeAdvancePhase()} internal function checks block timestamps against stored deadlines and advances the phase accordingly (Registration~$\to$~Ended if no voting window was opened in time, Voting~$\to$~Ended after the voting deadline), ensuring consistent behavior regardless of when transactions arrive. The read-only twin \texttt{currentPhase()} reports the same effective phase to view calls without writing storage.

\subsection{Registration Function}

\begin{lstlisting}[language=Java, caption={Voter registration: commitment insertion into the Merkle tree.}]
function register(uint256 _commitment)
    external inPhase(Phase.Registration)
{
    uint256 electionId = s_electionId;

    // Check 1+2: allowlisted, and not already registered
    if (!s_voters[electionId][msg.sender] ||
        s_hasRegistered[electionId][msg.sender]) {
        revert Voting__NotAllowedToVote();
    }
    // Check 3: commitment is unique
    if (s_commitments[electionId][_commitment]) {
        revert Voting__CommitmentAlreadyAdded(_commitment);
    }

    s_commitments[electionId][_commitment] = true;
    s_hasRegistered[electionId][msg.sender] = true;

    // Insert into the LeanIMT Merkle tree
    s_trees[electionId].insert(_commitment);

    emit NewLeaf(s_trees[electionId].size - 1, _commitment);
}
\end{lstlisting}

\subsection{Vote Function}

\begin{lstlisting}[language=Java, caption={Anonymous vote casting with ZK proof verification.}]
function vote(
    bytes memory _proof,
    bytes32 _nullifierHash,
    bytes32 _root,
    bytes32 _vote,
    bytes32 _depth
) external inPhase(Phase.Voting) {
    uint256 electionId = s_electionId;

    // Check 1: root is non-empty and matches the current tree
    if (_root == bytes32(0)) revert Voting__EmptyTree();
    if (_root != bytes32(s_trees[electionId].root()))
        revert Voting__InvalidRoot();

    // Check 2: valid candidate index
    uint256 candidateIdx = uint256(_vote);
    if (candidateIdx >= s_candidates.length)
        revert Voting__InvalidCandidate(candidateIdx);

    // Check 3: verify the ZK proof
    bytes32[] memory publicInputs = new bytes32[](4);
    publicInputs[0] = _nullifierHash;
    publicInputs[1] = _root;
    publicInputs[2] = _vote;
    publicInputs[3] = _depth;
    if (!i_verifier.verify(_proof, publicInputs))
        revert Voting__InvalidProof();

    // Check 4: nullifier not already used
    if (s_nullifierHashes[electionId][_nullifierHash])
        revert Voting__NullifierHashAlreadyUsed(_nullifierHash);
    s_nullifierHashes[electionId][_nullifierHash] = true;

    uint256 newCount = ++s_voteCounts[electionId][candidateIdx];
    emit VoteCast(_nullifierHash, msg.sender, candidateIdx,
                  block.timestamp, newCount);
}
\end{lstlisting}

\subsection{Factory Methods}

Because divisions are created \emph{on-chain at runtime}, the registry acts as a contract factory. Each division receives a fresh, isolated \texttt{Voting} instance sharing the single deployed verifier:

\begin{lstlisting}[language=Java, caption={Division creation via the factory pattern.}]
function createDivision(string calldata _name)
    external onlyOwner
    returns (uint256 divisionId, address votingContract)
{
    // Deploy a fresh Voting instance owned by the registry's
    // owner (admin), with the shared verifier. Question and
    // candidates are configured later via the admin UI.
    string[] memory emptyCandidates = new string[](0);
    Voting newVoting =
        new Voting(owner(), i_verifier, "", emptyCandidates);
    votingContract = address(newVoting);

    divisionId = divisions.length;
    divisions.push(Division({
        name: _name,
        votingContract: votingContract,
        gnOfficer: address(0),
        active: true
    }));

    emit DivisionCreated(divisionId, _name, votingContract);
}
\end{lstlisting}

A companion \texttt{addDivision()} registers an externally deployed contract, and \texttt{updateDivision()} rebinds a division's contract or GN officer.

\subsection{National Aggregation}

\begin{lstlisting}[language=Java, caption={National vote count aggregation across all active divisions.}]
function getNationalResults()
    external view returns (uint256[] memory totals)
{
    if (divisions.length == 0) return totals;

    // Candidate list is uniform across divisions in a national
    // election; take the count from the first division.
    string[] memory candidates =
        IVotingView(divisions[0].votingContract).getCandidates();
    totals = new uint256[](candidates.length);

    for (uint256 i = 0; i < divisions.length; i++) {
        if (divisions[i].active) {
            for (uint256 c = 0; c < candidates.length; c++) {
                totals[c] += IVotingView(
                    divisions[i].votingContract
                ).getVoteCount(c);
            }
        }
    }
}
\end{lstlisting}

\subsection{Design Rationale}

A citizen could otherwise enroll in multiple divisions using different device keys. The NicRegistry prevents this by storing a keyed hash of the National Identity Card number---never the NIC itself:

\begin{equation}
\text{nicHash} = \mathrm{HMAC}\text{-}\mathrm{SHA256}\big(\text{pepper},\ \text{canonicalNIC}\big)
\end{equation}

The NIC is first canonicalized (both the old \texttt{9-digit+V/X} and the new 12-digit formats are accepted), then hashed with a server-side secret pepper via HMAC-SHA256. Because the pepper is known only to the election authority, the small NIC number space cannot be brute-force enumerated from public blockchain state, yet any attempt to reuse a NIC deterministically collides with its earlier reservation.

\begin{lstlisting}[language=Java, caption={NicRegistry contract for cross-division Sybil prevention.}]
contract NicRegistry is Ownable {
    error NicRegistry__AlreadyUsed(bytes32 nicHash);

    mapping(bytes32 => bool) private usedNicHashes;
    mapping(address => bool) private s_votingContracts;

    event VotingContractUpdated(address indexed votingContract,
                                bool authorized);
    event NicHashReserved(bytes32 indexed nicHash);

    modifier onlyOwnerOrGN(address votingContract) {
        require(s_votingContracts[votingContract],
                "Unregistered division");
        require(msg.sender == owner() ||
                msg.sender == IVotingGN(votingContract).s_gnOfficer(),
                "Not owner or GN");
        _;
    }

    function setVotingContract(address _votingContract,
                               bool _authorized)
        external onlyOwner
    {
        s_votingContracts[_votingContract] = _authorized;
        emit VotingContractUpdated(_votingContract, _authorized);
    }

    function reserveNicHash(bytes32 nicHash,
                            address votingContract)
        external onlyOwnerOrGN(votingContract) returns (bool)
    {
        if (usedNicHashes[nicHash]) {
            revert NicRegistry__AlreadyUsed(nicHash);
        }
        usedNicHashes[nicHash] = true;
        emit NicHashReserved(nicHash);
        return true;
    }
}
\end{lstlisting}

Note that reservation is authorized per division: only the election authority or the GN officer \emph{of the named division contract} may reserve a hash, and the division must itself be registered with the NicRegistry.

\section{HonkVerifier.sol: Auto-Generated Proof Verifier}

The HonkVerifier is auto-generated by the Barretenberg toolchain from our Noir circuit and contains:
\begin{itemize}
    \item Hardcoded verification key (circuit-specific polynomial commitments)
    \item Proof deserialization logic
    \item Fiat--Shamir transcript reconstruction (Keccak flavor)
    \item BN254 pairing verification using the \texttt{ecPairing} precompile at address \texttt{0x08}
\end{itemize}

\begin{lstlisting}[language=Java, caption={Verifier interface and key constants.}]
interface IVerifier {
    function verify(
        bytes calldata _proof,
        bytes32[] calldata _publicInputs
    ) external view returns (bool);
}

// Constants baked in from the verification key
uint256 constant N = 32768;                  // 2^15 >= 19,278 gates
uint256 constant LOG_N = 15;
uint256 constant NUMBER_OF_PUBLIC_INPUTS = 4;
// Public input order: [nullifierHash, root, vote, depth]
\end{lstlisting}

The deployed verifier's runtime bytecode is 21{,}635 bytes---within the EIP-170 contract size limit of 24{,}576 bytes, which any EVM-compatible chain (including ours) enforces at deployment.

\section{Deployment Pipeline}

The contracts are deployed by \texttt{hardhat-deploy} scripts in strict dependency order:

\begin{enumerate}
    \item \texttt{PoseidonT3} library (used internally by LeanIMT)
    \item \texttt{LeanIMT} library, linked against PoseidonT3
    \item \texttt{HonkVerifier} (standalone, no dependencies)
    \item \texttt{Voting} demo instance, linked against LeanIMT, referencing the verifier
    \item \texttt{ElectionRegistry}, linked against LeanIMT (it deploys Voting instances itself), followed by \texttt{createDivision()} calls for the sample divisions
    \item \texttt{NicRegistry}, then \texttt{setVotingContract()} authorizations for each division
\end{enumerate}

Library linking is required because Solidity libraries with external functions must be deployed separately and their addresses embedded in the calling contract's bytecode at deploy time. Crucially, the \emph{same} deploy scripts target both backends: pointed at the local Hardhat network they populate chain id 31337, and pointed at the custom Go chain (Section~\ref{sec:go-chain}) they populate chain id 9494. The generated \texttt{deployedContracts.ts} artifact holds both entries side by side, which is what makes the two backends interchangeable at runtime.

\subsection{Design Rationale: A Generic, Contract-Agnostic EVM Node}

The defining design decision is that the node is \emph{completely ignorant of the election}. It does not know that \texttt{Voting.sol} exists; it executes whatever EVM bytecode is deployed to it and answers the same JSON-RPC methods an Ethereum node would. This property is not optional---it is forced by the contract layer itself: \texttt{ElectionRegistry.createDivision()} deploys new \texttt{Voting} contracts \emph{at runtime} from within the EVM, which no fixed-contract blockchain design can accommodate.

The consequences are far-reaching:

\begin{itemize}
    \item \textbf{Zero coupling to contract changes.} When a contract is modified, the standard workflow (recompile, redeploy with \texttt{hardhat-deploy}) is the entire migration. No node code changes, ever.
    \item \textbf{All clients work unchanged.} The mobile app (viem raw transactions), the Next.js API routes (\texttt{eth\_call}, \texttt{eth\_getLogs}), the web portals, and the block explorer all already speak JSON-RPC; switching them to the custom chain is an environment-variable change (RPC URL and chain id), not a code change.
    \item \textbf{Backend swappability.} The system runs identically on the Hardhat development network (chain id 31337) and on the custom chain (chain id 9494). Both remain first-class targets, switchable per deployment.
    \item \textbf{Identical error semantics.} Reverts surface as standard Ethereum revert errors carrying the ABI-encoded custom error in the \texttt{data} field, so client-side error handling (e.g.\ detecting \texttt{Voting\_\_NullifierHashAlreadyUsed} to show ``you have already voted'') behaves identically on both backends. This compatibility is enforced by differential testing against a real Hardhat node (Chapter~\ref{ch:testing}).
\end{itemize}

\subsection{Transaction Lifecycle and Block Production}

The node uses \emph{auto-mining with one transaction per block}, the same model the Hardhat development network popularized. There is no mempool and, because a single sequencer orders all transactions, there are no forks and no reorganizations---every sealed block is instantly final.

\begin{figure}[H]
\centering
\includegraphics[width=0.92\textwidth]{Images/fig_chain_v2_tx_lifecycle.png}
\caption{Transaction lifecycle: validation and EVM execution happen before a block exists; a reverting transaction is rejected at submission and never enters the chain, keeping history free of failed transactions.}
\label{fig:tx-lifecycle}
\end{figure}

A submitted raw transaction passes through four stages. \emph{Validation} recovers the sender from the signature (rejecting wrong-chain-id transactions), enforces the exact expected nonce, and checks the gas limit against the block gas limit of 60~million---comfortably above the ${\sim}15$~million gas a proof-verifying vote may consume. \emph{Execution} applies the transaction to a copy of current state through go-ethereum's transition logic, producing a receipt with logs and bloom filter. \emph{Sealing} assembles a post-merge-style header (strictly increasing timestamps, zero base fee, transaction/receipt/state roots) around the single transaction. \emph{Persistence} writes block, receipts, lookup entries, and the committed state trie in one atomic batch, ordered so that a crash mid-write always leaves the previous head intact.

If execution reverts, the sequencer rolls back and returns the revert data through the RPC error---the transaction is never mined. This mirrors Hardhat's auto-mine behavior exactly, which is what keeps client error handling backend-agnostic.

\subsection{Gasless Execution Model}

Gas fees are the reason no public chain is acceptable for a national election, and eliminating them is a first-class design goal rather than a patch:

\begin{itemize}
    \item The base fee is zero in every block, and the node's fee oracle methods (\texttt{eth\_gasPrice}, \texttt{eth\_maxPriorityFeePerGas}, \texttt{eth\_feeHistory}) all report zero, so standard client libraries automatically construct zero-cost transactions.
    \item Transactions with a gas price of zero are fully valid. Gas is still \emph{metered}---the EVM's gas accounting is unchanged and serves as denial-of-service protection---but no balance is ever deducted.
    \item Consequently, a freshly generated burner wallet with a \textbf{zero balance} can submit a vote directly. The development-mode faucet and any future ERC-4337 paymaster infrastructure become unnecessary on this chain, and the funding-trail deanonymization vector (tracing a burner back through whoever funded it) disappears entirely.
    \item The genesis block prefunds the twenty standard development accounts, so deployment tooling and the existing faucet continue to work unmodified in hardhat-compatible workflows. Nonces remain strictly enforced for all senders.
\end{itemize}

\subsection{Replicated Topology: Sequencer and Verifying Replicas}

\begin{figure}[H]
\centering
\includegraphics[width=0.92\textwidth]{Images/fig_chain_v2_replication.png}
\caption{Three-node topology: the sequencer pushes each sealed block over mutually authenticated TLS; replicas independently re-execute every transaction and refuse any block whose state root does not match, making history tampering immediately evident.}
\label{fig:replication}
\end{figure}

The production deployment runs three nodes: one \textbf{sequencer} and two \textbf{verifying replicas} (the replica count is configuration, not code). Replication serves two distinct purposes:

\begin{enumerate}
    \item \textbf{Read scalability and availability.} Replicas serve the full read RPC surface locally---results dashboards, audit queries, and explorer traffic never load the sequencer. Write transactions submitted to a replica are transparently forwarded.
    \item \textbf{Tamper evidence.} Replicas are not passive mirrors. Each received block is fully \emph{re-executed} on the replica's own state, and the resulting state root is compared against the header. A sequencer that alters history or fabricates state produces a root mismatch that every honest replica rejects and logs loudly. Combined with deterministic replay (below), this gives the permissioned deployment an honest integrity story without the complexity of Byzantine consensus: the sequencer is a liveness single point, but it \emph{cannot silently falsify} the record.
\end{enumerate}

Node-to-node traffic runs over mutual TLS with a private certificate authority; replicas catch up after downtime by pulling missed block ranges and re-verifying each one.

\subsection{Independent Auditability}

Because state is a pure function of the ordered block list, anyone with a copy of the data directory can re-derive the entire election. The standalone \texttt{audit} tool replays every block from genesis on a fresh state database---re-executing every registration, every proof-verifying vote, and every administrative action---and verifies, per block: the state root, receipt root, transaction root, gas usage, parent linkage, and timestamp monotonicity. A single flipped byte anywhere in history is pinpointed to the exact block and field. This is the operational realization of end-to-end verifiability at the infrastructure layer, complementing the cryptographic verifiability provided by the ZK proofs themselves.

\subsection{Administrative Authentication without Wallets}\label{sec:no-wallet-auth}

Browser wallet extensions (MetaMask) are a usability and operational liability for election staff: key custody falls on individuals, and every action requires a signing pop-up. On the custom chain, wallet connections are removed from the web application entirely and replaced by a credential-based scheme; the chain's on-chain authorization model (\texttt{onlyOwner}, \texttt{onlyOwnerOrGN}, allowlists, proof verification) is unchanged---only the custody of signing keys moves.

\begin{figure}[H]
\centering
\includegraphics[width=0.92\textwidth]{Images/fig_chain_v2_auth_relay.png}
\caption{Wallet-free administration: admin and GN officers authenticate with credentials; a server-side relay signs only whitelisted contract functions with role-scoped keys. Voters never pass through the relay---registration and voting go directly from the device to the chain.}
\label{fig:auth-relay}
\end{figure}

\begin{itemize}
    \item \textbf{Election admin} signs in with a username and password (bcrypt-hashed, session cookie, rate-limited with lockout). A server-side \emph{relay} holds the contract-owner key and signs administrative transactions on the admin's behalf---but only functions on a fixed whitelist (question, candidates, phase transitions, division management). Every relayed action is appended to an audit log.
    \item \textbf{GN officers} receive per-officer accounts created by the admin. Each account maps to a server-generated keypair (encrypted at rest) whose address is bound on-chain via \texttt{setGNOfficer()}. The relay additionally scope-checks GN calls: an officer can invoke \texttt{addVoters} and \texttt{reserveNicHash} \emph{only} against their own division's contract.
    \item \textbf{Voters} are untouched by this scheme. The mobile app's hardware-keystore key signs registration directly, and votes are submitted from throwaway burners straight to the chain---routing voter traffic through a server would undermine the anonymity design, so the relay is structurally incapable of signing \texttt{register} or \texttt{vote}.
\end{itemize}

A compromise of the relay server is therefore bounded: an attacker could operate the election lifecycle (detectable in the audit log and on-chain), but could not forge a single vote (which requires a valid ZK proof) nor double-count one (nullifier uniqueness is enforced by the contract).

\subsection{Backend Swappability}

Switching the entire application between the Hardhat network and the custom chain requires starting the target chain, running the deploy scripts against it once, and changing environment variables (backend flag, RPC URL, chain id) in the web and mobile configurations. No source file changes in either direction. This was an explicit acceptance criterion, and it also preserves the Hardhat network as the fast inner-loop development environment while the custom chain serves as the deployment target.

\section{Summary}

This chapter presented the complete smart contract layer---\texttt{Voting.sol}'s phased state machine with five-layer vote validation, \texttt{ElectionRegistry.sol}'s on-chain division factory with national aggregation, \texttt{NicRegistry.sol}'s peppered-hash Sybil prevention, and the auto-generated \texttt{HonkVerifier}---and the custom Go blockchain that executes it. By embedding a real EVM behind the standard Ethereum JSON-RPC interface, the chain remains completely contract-agnostic: it provides gasless voting, instant finality, replicated tamper-evident persistence, full-history auditability, and wallet-free administration, while every application component (Chapter~\ref{ch:applications}) interacts with it exactly as it would with any Ethereum node.
