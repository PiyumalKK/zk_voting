\chapter{Testing, Results, and Evaluation}\label{ch:testing}

This chapter presents the comprehensive testing methodology, test results, performance measurements, gas analysis, security evaluation, and comparative analysis of our system. We evaluate the system against its stated objectives and compare it with existing solutions.

\section{Testing Methodology}

Our testing strategy follows a four-tier approach:

\begin{enumerate}
    \item \textbf{Unit Testing}: Individual contract functions and circuit constraints
    \item \textbf{Integration Testing}: Cross-component interactions (circuit $\to$ verifier $\to$ contract)
    \item \textbf{End-to-End Testing}: Complete voting flow (mobile $\to$ API $\to$ chain $\to$ verification)
    \item \textbf{Security Testing}: Adversarial inputs, edge cases, attack simulations
\end{enumerate}

\subsection{Key Test Cases}

\subsubsection{Registration Tests}

\begin{lstlisting}[language=Java, caption={Registration test: allowlisted voter can register successfully.}]
it("should allow a registered voter to register commitment", 
  async () => {
    // Setup: add voter to allowlist
    await voting.addVoters([voter.address], [true]);
    await voting.startRegistration(3600);
    
    // Generate commitment
    const nullifier = 42n;
    const secret = 123n;
    const commitment = poseidon2([nullifier, secret]);
    
    // Register
    await expect(voting.connect(voter).register(commitment))
      .to.emit(voting, "NewLeaf")
      .withArgs(0, commitment);
    
    // Verify state
    const data = await voting.getVoterData(voter.address);
    expect(data.registered).to.be.true;
});
\end{lstlisting}

\subsubsection{Double-Vote Prevention Tests}

\begin{lstlisting}[language=Java, caption={Test: nullifier hash reuse is rejected.}]
it("should reject vote with used nullifier hash", async () => {
    // First vote succeeds
    await voting.connect(burner1).vote(
      proof, nullifierHash, root, vote, depth
    );
    
    // Second vote with same nullifier reverts
    await expect(
      voting.connect(burner2).vote(
        proof, nullifierHash, root, vote, depth
      )
    ).to.be.revertedWithCustomError(
      voting, "NullifierHashAlreadyUsed"
    ).withArgs(nullifierHash);
});
\end{lstlisting}

\subsection{Coercion Resistance Analysis}

\begin{figure}[H]
\centering
\includegraphics[width=0.85\textwidth]{Images/fig_anonymity_set_diagram.png}
\caption{Anonymity set visualization: a voter's ballot is indistinguishable among all registered voters in the division.}
\label{fig:anonymity-set}
\end{figure}

Our system provides \textbf{partial coercion resistance}:
\begin{itemize}
    \item \textbf{Protected against}: Post-vote coercion (voter cannot prove how they voted after the fact, as the burner wallet is discarded)
    \item \textbf{Vulnerable to}: Real-time coercion (adversary physically present during voting can observe the screen)
    \item \textbf{Mitigation}: The OTP step creates a time window; the actual proof generation and submission can be separated from candidate selection
\end{itemize}

Full coercion resistance would require re-voting capability (as in MACI) or deniable encryption---identified as future work.

\section{Observations and Discussion}

\subsection{Proof Generation Time}

The 15--25 second proof generation time on mobile is the primary user experience bottleneck. While acceptable for a once-per-election action, this could be reduced to $<$5 seconds with native proving (Swoir/noir\_android)---identified as future work.

\subsection{Hermes Compatibility Trade-offs}

The Hermes BigInt limitation forced a WebView-based architecture for proof generation. While this adds complexity, it provides a clean separation between the UI layer (Hermes) and the cryptographic layer (system WebView with full BigInt support).

\subsection{Gas Efficiency}

The vote function's 350,000 gas cost is dominated by proof verification (280,000 gas for the BN254 pairing). On our gasless chain this is free, but for future L2 deployment, this could be reduced by:
\begin{itemize}
    \item Batch verification (multiple proofs in one pairing)
    \item Recursive proofs (aggregate many votes into one proof)
    \item Optimized verifier circuits
\end{itemize}

\subsection{Multi-Division Trade-offs}

The factory pattern provides excellent isolation and administrative delegation but introduces aggregation overhead. The \texttt{getNationalResults()} function must iterate across all 160 divisions---a $O(n)$ operation. For 160 divisions this is negligible (15ms), but would need optimization for thousands of divisions.

\section{Summary}

Our comprehensive evaluation demonstrates:
\begin{enumerate}
    \item \textbf{Correctness}: All 54 unit tests pass; cross-layer test vectors verify consistency
    \item \textbf{Performance}: Vote submission completes in $<$30 seconds end-to-end
    \item \textbf{Security}: All identified attack vectors are either prevented or detected
    \item \textbf{Scalability}: Architecture supports 10.5M voters without circuit modification
    \item \textbf{Cost}: Zero gas fees for voters (gasless chain)
    \item \textbf{Privacy}: Formal voter--ballot unlinkability (Theorem~\ref{thm:unlinkability})
\end{enumerate}
